# AI Tuition Assistant – SE 4458 Midterm (Group 1)

Student: Yasmin Malgir. A conversational assistant for tuition questions that combines an **LLM agent with real
function calling**, a separate **MCP server** for policy search, a **versioned REST API on PostgreSQL**, and an
**API gateway** that every REST call passes through.

```
Student ──► Agent (Express + LLM tool calling) ──► LLM (Gemini, OpenAI-compatible endpoint)
              │  MCP client                         ▲ tool results go back to the LLM
              ├──────────► MCP server ──► indexed University_Tuition_Policies.md   (search_tuition_policies)
              └─ REST ───► API gateway (Azure API Management) ──► Tuition API (/api/v1) ──► PostgreSQL
```

|---|---|---|

| MCP server (`search_tuition_policies`) | `mcp-server/` | Node 22, official MCP TypeScript SDK, Streamable HTTP |

## 1. How the agent works

1. The student logs in with the same credentials as the REST API (`POST /api/login` on the agent forwards to
   `POST /api/v1/auth/login` **through the gateway**). The JWT is kept server-side in the session and is never shown to the LLM.
2. Each chat message goes to the LLM together with four tool definitions: the MCP tool `search_tuition_policies(query)` and the
   REST-backed tools `get_my_tuition(term?)`, `request_payment(term, amount)` and `submit_confirmed_payment()`. The **LLM chooses**
   which tools to call (real tool/function calling, no keyword routing).
3. The agent executes the calls: MCP over Streamable HTTP for policies, REST via `GATEWAY_URL` for live data. Results are
   returned to the LLM, which writes the grounded answer and cites policy section numbers.
4. **Payments need explicit confirmation.** `request_payment` only prepares a payment (nothing is charged) and the student sees a summary.
   `submit_confirmed_payment` calls the payment API, and only after a separate, explicit confirmation message ("yes", "evet", …) executes it. This check is
   deterministic code (`agent/src/confirmation.ts`), not left to the LLM; questions, negations and messages that change the
   amount do not count as consent. The payment's `transactionId` is generated by the agent, so a repeated confirmation cannot double-charge (the API rejects duplicates with 409).
5. `/api/chat` returns the reply plus a **tool trace** (tool name, input, result) that the UI renders for the demo.

Endpoints of the agent: `POST /api/login`, `POST /api/chat`, `POST /api/logout`, `GET /health`, UI at `/`.

## 2. MCP server and indexing

`mcp-server/docs/University_Tuition_Policies.md` is split into chunks by Markdown headings (section numbers such as `3.1` are kept
as references) and a full-text index is built **once at start-up**, not per query (`chunker.ts`, `searchIndex.ts`,
`indexLoader.ts`). The server exposes one tool, `search_tuition_policies(query)`, which returns the best-matching excerpts with their
section references. It runs as a separate process/container (`POST /mcp`, `GET /health`) and is protected with `MCP_AUTH_TOKEN`
(`Authorization: Bearer <token>`; without or with a wrong token `POST /mcp` returns `401`). Deployed on Azure it is reachable only with that token (see section 5).
The policy document is **not** the tuition database; balances come only from the REST API.

## 3. REST API (all routes under `/api/v1`)

| Method & path | Caller | Auth | Notes |
|---|---|---|---|
| `POST /auth/login` | all | none | `{username, password}` → `{accessToken, tokenType, expiresIn}` |
| `GET /tuition/mobile/{studentNo}` | Mobile app | **none** | `?term=` optional. **3 calls per student per day** (per `studentNo`, not just IP); 4th call → `429` + `Retry-After` |
| `GET /tuition/{studentNo}` | Banking app | JWT (student, own record) | `?term=2026-FALL` → TERM balance; without `term` → OVERALL balance (`scope` field says which) |
| `POST /tuition/payments` | Banking app | JWT (student, own record) | `{studentNo, term, amount, transactionId}`; duplicate `transactionId` → 409, amount above balance → 422 |
| `POST /admin/tuition` | Admin site | JWT (admin) | create-or-update tuition for `(studentNo, term)` |
| `POST /admin/tuition/batch` | Admin site | JWT (admin) | CSV `studentNo,term,amount,currency`; returns success/failure counts per row |
| `GET /admin/tuition/unpaid` | Admin site | JWT (admin) | `term`, `page`, `pageSize`; paged |
| `GET /health` | all | none | liveness |

Swagger UI: `/api-docs`; OpenAPI document: `/openapi.json` (the gateway API was imported from it).

Design decisions (documented as the assignment asks):
- **Balance scope:** with `term` the response is that term's balance, otherwise the overall balance across all terms; the response contains `scope: "TERM" | "OVERALL"`.
- **Add Tuition duplicates:** the same `(studentNo, term)` updates the amount (upsert); an amount below what was already paid is rejected so a balance can never become negative.
- **Term format:** `YYYY-FALL | YYYY-SPRING | YYYY-SUMMER`. Money has at most two decimals, currency is carried per tuition record.
- **Daily limit:** counted in `Europe/Istanbul` local days in the `query_log` table, enforced in the API so it works even if callers change IP.
- **Authentication:** HS256 JWT (issuer `tuition-api`, audience `tuition-clients`, 1 h), claims `role` and `studentNo`; students can only read/pay their own record; bcrypt password hashes.
- **Gateway lock:** when `GATEWAY_SECRET` is set, every `/api/v1/*` request must carry `X-Gateway-Secret` (added by the gateway); otherwise `403 GATEWAY_REQUIRED`. `/health`, `/openapi.json` and `/api-docs` stay open.

Database: PostgreSQL (`students`, `users`, `tuitions`, `payments`, `query_log`); schema in `api/db/schema.sql`, diagram in
[`docs/er-diagram.md`](docs/er-diagram.md). The schema is applied idempotently at start-up; demo data (fictitious students
`20260001`–`20260005`, tuition and two payments) is loaded when `SEED_DEMO_DATA=true`. Demo passwords are **never in the repo**; they come from
`SEED_STUDENT_PASSWORD` / `SEED_ADMIN_PASSWORD`.

## 4. API gateway (Azure API Management, Consumption tier)

All REST calls, including the agent's, go through `https://<apim-name>.azure-api.net`. The API is imported from `/openapi.json`
with an empty URL suffix, so the public paths are the same `/api/v1/...` routes; the backend is the Container App's HTTPS URL.
Policy: [`gateway/apim-api-policy.xml`](gateway/apim-api-policy.xml). It references two APIM *Named Values* (secret type), never literal secrets:

- `gateway-secret`: added to every backend call as `X-Gateway-Secret` (header overridden, so clients cannot forge it).
- `jwt-signing-key-b64`: Base64 of the API's `JWT_SECRET`, used by `validate-jwt` (HS256, issuer/audience/expiry checked, `401` on failure).

Route mapping: public (no JWT) = `POST /api/v1/auth/login`, `GET /api/v1/health`, `GET /api/v1/tuition/mobile/{studentNo}`;
JWT required = `/api/v1/tuition/*` banking routes and payments; JWT with `role=admin` required = `/api/v1/admin/*`.
Example gateway error responses: missing/invalid token → `401`; backend reached without the secret → `403 GATEWAY_REQUIRED`.
The daily limit is not done at the gateway (`rate-limit-by-key` is not available on the Consumption tier); the API enforces it per student.

The resources are scale-to-zero, so the first request after idle time is slow (cold start). Credentials are **not** in this repository:
demo accounts are students `20260001`-`20260005` and `admin`; their passwords are set through `SEED_*` environment variables
(Azure secrets) and are given to the instructor separately. To reproduce everything with your own passwords, use section 6 (local run).

Decisions and limitations of the deployed setup:
- **MCP is exposed with external ingress + shared token.** The Container Apps *Express* environment does not route app-to-app calls through internal
  ingress (measured from inside the agent container: the internal FQDN resolved to the environment's public address and answered `404`; see `docs/deployment.md`).
  So the MCP app has external ingress (HTTPS only) and every `POST /mcp` must carry `MCP_AUTH_TOKEN`. The MCP path is intentionally separate from the API gateway path.
- **LLM:** Gemini through its OpenAI-compatible endpoint, model `gemini-3.5-flash-lite`, API key from Google AI Studio (no paid plan was enabled).
  `gemini-flash-latest` returned `503 UNAVAILABLE` (high demand) during testing, so it was replaced. Gemini 3 models return a `thought_signature` with each
  tool call that must be sent back; the agent preserves it (`extra_content`, `agent/src/llm.ts`, `agent/src/agent.ts`). The key is revoked after grading.
- **Daily limit** (3 mobile queries per student per day) is enforced in the API, keyed by student number; APIM Consumption has no daily `rate-limit-by-key`.
- **Not implemented:** login brute-force throttling at the gateway; real card processing (payments are simulated, as the assignment says).
- PostgreSQL uses verified TLS; its firewall allows Azure services (a managed-database firewall rule, not open to the internet at large).

## 6. Running locally

```bash
cp .env.example .env          # fill in CHANGE_ME values (no real secrets in git)
docker compose up --build     # db + api + mcp + agent; no gateway locally (dev only)
# agent UI  http://localhost:3200      Swagger  http://localhost:3000/api-docs
```
Without Docker: `cd api && npm ci && npm start` (needs PostgreSQL and `DATABASE_URL`), `cd mcp-server && npm ci && npm run dev`, `cd agent && npm ci && npm run dev`.

Environment variables are listed in [`.env.example`](.env.example). Cloud steps are in [`docs/deployment.md`](docs/deployment.md).
